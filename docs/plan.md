# Code Documentation Plan

## Summary

- Cover live handwritten Go code with English GoDoc.
- Exclude generated files, golden snapshots, and other autogenerated artifacts.
- Prioritize user-facing runtime packages first, then internal and CLI code, then executable examples and audit.

## Rules

- Every exported package needs a package comment or `doc.go`.
- Every exported type, function, method, constant, and variable needs GoDoc.
- Every exported struct field needs a comment that explains behavior or contract.
- Non-trivial internal code should explain stage, purpose, or behavior without restating syntax.
- Key public workflows should have executable `Example...` tests.

## Execution Order

1. Documentation baseline in `AGENTS.md` and `docs/dev.md`.
2. Public runtime packages in `sdk/`, `app/`, and `pkg/`.
3. Infra clients and loaders.
4. Handwritten example code.
5. Internal packages.
6. CLI packages.
7. Executable examples for key public APIs.
8. Final audit for missing comments and style consistency.

## Acceptance Criteria

- Every live handwritten exported package has package documentation.
- Every live handwritten exported symbol has GoDoc.
- Every exported field in live handwritten public structs has a field comment.
- Key public packages have executable `Example...` tests.
- `go test ./...`, `go vet ./...`, and `go build ./...` stay green.
